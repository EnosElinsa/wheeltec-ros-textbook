# 5. ROS 2 程序怎样协作

## 本章要回答的问题

第 4 章用话题连续传递文字。机器人还有“一次询问”“耗时任务”和“修改设置”等需求，它们应该怎样表达？本章依次介绍话题、服务、动作和参数，并把这些概念放回一台轮式机器人的数据链路。

## 从一个具体场景开始

机器人运行时会同时发生几类事情：雷达持续产生距离，程序偶尔查询某项状态，导航需要几秒甚至几分钟才能到达目标，节点还要保存速度限制等设置。

这些数据的时间特点不同。把它们全部塞进一种通信方式，会让程序难以判断何时回复、怎样报告进度，以及谁拥有某项设置。ROS 2 因此提供了几种用途不同的协作方式。

## 新概念

### 话题：什么数据会持续到来

话题适合连续产生、接收方数量可能变化的数据。发布者把消息送到话题，订阅者按需接收；发布者不必等待每个订阅者逐一回复。

常见例子有激光扫描、摄像头图像、车轮里程和速度目标。第 4 章的 `/chatter` 也是话题。

### 服务：什么询问需要一次回答

服务用于一次请求和一次响应。客户端提出问题，服务端处理后返回结果。它适合执行时间较短、调用方需要明确答复的操作，例如读取某项状态或触发一次保存。

服务不适合持续传感器数据，也不适合需要不断报告进度的长任务。

### 动作：什么任务需要时间、进度和取消

动作适合持续一段时间的任务。客户端提交目标，执行端可以接受或拒绝，执行过程中返回进度，最后给出结果；客户端也可以请求取消。

“移动到地图中的某个位置”是典型动作。机器人可能需要规划路线、绕开障碍并不断更新剩余距离，无法用一次立即返回的服务完整表达。

### 参数：什么设置属于一个节点

参数是节点拥有的配置值，例如端口名称、速度上限或某个开关。参数用于描述“这个节点应怎样工作”，不是持续传递传感器数据。

修改参数前应先确认名称、类型和生效方式。有些参数可以在运行中调整，有些设置需要重新启动节点才会采用。

## 图示或逐步例子

下面是一条简化的机器人数据链：

```text
雷达节点 → 扫描消息 → 导航节点 → 速度消息 → 底盘节点 → 控制板 → 电机
```

逐步看这条链：

1. 雷达节点持续发布扫描消息，因此使用话题。
2. 导航节点订阅扫描数据，结合目标计算下一步速度。
3. “前往某个位置”需要时间和进度，因此通常由动作表达。
4. 导航程序持续产生速度消息，底盘节点通过话题接收。
5. 底盘节点把速度要求转换成控制板能够理解的数据。
6. 控制板读取车轮反馈并调节电机。

服务可能出现在“保存地图”或“查询状态”等一次性操作中。参数则保存节点自己的配置，例如最大速度。它们与主数据链配合，但不取代持续的话题数据。

### 选择方法

遇到新的数据需求时，按下面顺序提问：

| 问题 | 合适的方式 |
|---|---|
| 数据会持续产生，接收方只需按需订阅吗？ | 话题 |
| 是一次请求，并且能够较快返回一次结果吗？ | 服务 |
| 任务需要时间、进度、结果或取消吗？ | 动作 |
| 这是某个节点自己的设置吗？ | 参数 |

## 可选实验

不用启动机器人，选择下列需求并判断适合哪种方式：

1. 摄像头每秒产生多张图像。
2. 请求系统保存一次当前地图。
3. 命令机器人前往房间门口，并显示执行进度。
4. 把底盘节点的最大速度设置为一个较低值。

再为自己的项目补充两个例子，并写下选择理由。答案不应只写名称，还要说明数据是持续的、一次性的、耗时的，还是节点配置。

## 本章小结

节点根据数据的时间特点选择协作方式：话题传递连续消息，服务处理一次请求与响应，动作表示可反馈和可取消的耗时任务，参数保存节点配置。机器人完整链路往往同时使用多种方式。

后续章节还会介绍程序怎样组织成项目、消息怎样带上时间和坐标含义，以及不同程序为何偶尔无法匹配。现在只需掌握本章四种方式的用途。
