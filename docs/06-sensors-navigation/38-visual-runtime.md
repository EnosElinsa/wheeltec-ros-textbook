# 38. 视觉建图与导航的运行过程

本章按数据经过的先后，写这台 R680 如何只靠车头的深度相机建立地图，再在地图上定位并导航到目标点。实机图像取自车上抓取，示意图与数据流图由本章配图脚本生成。

---

# 过程概要 {#vision-nav-code-resource}

建图和导航共用前半段过程。深度相机拍下红外图像并算出深度图像，本项目的配对节点从中挑出没有散斑的红外和投射器打开时算出的深度，再合成一条消息（第 1 节）。

视觉里程计由这条消息估计车相对本次出发的运动。底盘另外给出轮速和陀螺仪角速度，三份材料融合成一条平滑的运动（第 2 节）。

图像里的点、车身和场地各有自己的坐标系，坐标变换把它们接成一条链，任一时刻都能把镜头前的点换到场地上（第 3 节）。

建图时，RTAB-Map 沿途写入地点记录，由距离拼出占用栅格，并在车回到旧地点时用回环修正位置（第 4 节）。导航时不再写入新记录，RTAB-Map 在已有地图上识别当前位置（第 5 节）。Nav2 在代价地图上规划到目标的路径（第 6 节），再按路径计算速度，经本项目的看门狗发给底盘（第 7 节）。第 8 节分析这套只用相机感知环境的方案还存在哪些问题，以及可能的改进方向。

# 1. 采集红外图像和深度图像

这一节从相机开始。RealSense 驱动由左右红外算出深度图像，并让投射器逐帧交替开关。本项目的配对节点判断每一帧投射器的开关状态，把无散斑的红外和相邻一帧的深度放在一起，再由 RTAB-Map 的同步节点合成一条消息。三个小节依次写深度图像的由来、投射器交替与配对、合成一条消息。

## 1.1 由左右红外得到深度图像

RealSense 驱动在相机内比较左右两幅红外图像，由同一处在两幅图像上的位置之差算出距离，得到深度图像。

### 左红外、右红外与基线

本机深度相机型号为 D435C。机身正面从左到右是左红外镜头、彩色镜头、右红外镜头和红外投射器。投射器是一个红外光源，它把许多细小的红外光点投到车前方的物体上，左右红外镜头都能拍到这些光点。

![深度相机正面。从左到右为左红外镜头、彩色镜头、右红外镜头和红外投射器](./assets/realsense-d435-commons.jpg)

深度图像不是某一个镜头直接拍出来的，而是由左右红外同时拍到的同一个物体算出来的。两个镜头左右分开，同一个物体在两幅图像上的水平位置因此不同。

### 视差

一幅图像由按行、列排列的像素组成。水平方向从左向右数，像素的序号称为列号 $u$。竖直方向从上向下数，序号称为行号 $v$。左上角的像素是第 0 列、第 0 行。

![左上角为第 0 列、第 0 行。列号 u 向右增加，行号 v 向下增加](./assets/pixel-row-col.png)

驱动在左红外某一行选定一个像素，连同周围像素组成一个窗口。右红外停在同一行，以某一列为中心取同样大小的窗口，把两个窗口里相对位置相同的像素的亮度相减，再把差的绝对值相加。右图窗口从左图像素所在的列开始，每次向左移动 1 列，和最小的那一次就是同一处。此时左图列号减去右图列号，称为**视差**（Disparity），记为 $d$，单位是像素。两个镜头中心之间的距离称为**基线**（Baseline），记为 $B$。下图中的五角星是同一个物体，左右两个平面是它在两个镜头上的成像。

![同一物体在两个红外镜头上的成像。Disparity 为视差，Baseline 为基线](./assets/realsense-stereo-ssd.png)

### 由视差得到距离

视差与距离成反比。物体越近，两条视线的夹角越大，同一个物体在两幅图像上隔得越开，视差越大。物体很远时，两条视线几乎平行，视差接近 0。

镜头正前方成像的平面称为像平面，它到镜头中心的距离是焦距，以像素为单位记为 $f_x$。把右镜头的视线平移到左镜头，就与左视线在像平面上截出一段，长度正是视差 $d$。下图中红色小三角形的底是 $d$、高是 $f_x$，蓝色大三角形的底是基线 $B$、高是物体到镜头的距离 $Z$。平移后的右视线与原来的右视线平行，两个三角形因此相似：

![红色小三角形的底是视差 d、高是焦距；蓝色大三角形的底是基线 B、高是距离 Z。红色虚线是右视线平移到左镜头后的位置](./assets/stereo-similar-triangles.png)

$$
\frac{d}{f_x} = \frac{B}{Z}
\qquad\Longrightarrow\qquad
Z = \frac{f_x\,B}{d}.
$$

本机红外的 $f_x = 421.374$，基线 $B = 0.050\,\mathrm{m}$。某处的视差为 $20$ 个像素时，$Z = 421.374 \times 0.050 / 20 \approx 1.05\,\mathrm{m}$。视差为 $7$ 个像素时，$Z \approx 3.0\,\mathrm{m}$。驱动把算出的距离乘以 1000，以毫米为单位的整数写入深度图像。

### 得到深度图像

驱动把左红外第 $v$ 行、第 $u$ 列算出的 $Z$ 写进深度图像同一个位置 $(u, v)$。右红外只用来得到视差，不存放距离。深度图像因此与左红外共用左镜头的中心，计算时所有视线都看成从这一点穿出，这一点称为**光学中心**（Optical Center）。

两个镜头之间的平移和转动称为**外参**（Extrinsic Parameters）。平移是三个数 $(t_x, t_y, t_z)$，单位 m，转动是一个 $3 \times 3$ 矩阵。深度图像与左红外共用光学中心和像素位置，所以两者之间既没有平移，也没有转动：

$$
(t_x, t_y, t_z) = (0,\ 0,\ 0),
\qquad
\text{转动} = \begin{bmatrix} 1 & 0 & 0 \\ 0 & 1 & 0 \\ 0 & 0 & 1 \end{bmatrix}.
$$

主对角线为 1、其余为 0 的矩阵称为单位矩阵，它表示不转动。左红外到右红外的转动同样是单位矩阵，平移只在基线方向上有 $t_x = 0.050\,\mathrm{m}$，即右红外在左红外右侧 50 mm。

### 发布左红外图像与深度图像

深度图像已经按左红外的像素排好距离，驱动因此只打开左红外和深度两路，把它们作为两幅图像发布出去。每一路还配有一条相机信息，存放该镜头出厂时测好的固定参数，其中就有上面用到的焦距。

```yaml
# /camera/infra1/image_rect_raw  类型 sensor_msgs/msg/Image，左红外，每帧一条
header:
  stamp: ...                          # 拍摄时刻
  frame_id: camera_infra1_optical_frame   # 图像所在的坐标系：左红外的光学中心
height: 480                           # 行数
width: 848                            # 列数
encoding: "mono8"                     # 每个像素 1 字节，表示亮度
step: 848                             # 每行占的字节数
data: [ ... ]                         # 848 × 480 个亮度值，按行排开

# /camera/depth/image_rect_raw  类型 sensor_msgs/msg/Image，深度图像
encoding: "16UC1"                     # 每个像素 2 字节，距离，单位 mm，0 表示没有有效距离
step: 1696                            # 848 列 × 2 字节

# /camera/infra1/camera_info、/camera/depth/camera_info  类型 sensor_msgs/msg/CameraInfo
# 与对应的图像配套，存放焦距等固定参数，2.1 用到
```

下图是同一时刻的左红外和深度图像。左红外的灰度就是亮度。深度图像的像素位置与左红外相同，近处亮灰、远处暗灰，黑色表示没有有效距离。

## 1.2 投射器交替与配对

驱动发出的红外里，相邻两帧并不一样。RealSense 驱动让投射器一帧打开、一帧关闭，本项目的配对节点再判断每一帧属于哪一种，并据此决定取哪一帧的红外、哪一帧的深度。

### 投射器为什么交替开关

左右比较出距离和前后帧找同一个点，对投射器的要求相反。

左右比较依据的是亮度图案。白墙和地面上亮度几乎处处相同，同一行上比较不出哪里是同一处。投射器打开后，场景上多出许多细小的亮点，称为**散斑**（Speckle），左右两幅图像上就有了可以比较的图案，墙面和地面也能算出距离。

前后帧找同一个点依据的是场景本身的亮度。投射器装在相机上，与镜头一起移动，散斑落在场景上的位置随车一起变化，而不是固定在墙上。落在散斑上的特征点在前后帧里几乎停在同一个像素，视觉里程计会误以为车没有动，回环识别也会把两处不同的地方当成同一处。做前后帧匹配的红外因此必须是投射器关着时拍下的。

一帧不能同时开和关，驱动于是逐帧交替：投射器打开的那一帧用来算深度，关闭的那一帧用来找特征点。下图是相邻两帧左红外。左边投射器关着，柜门、墙和地面是成片的灰度。右边投射器开着，同样的位置布满细碎的亮点。

![相邻两帧左红外。左边投射器关着，墙和地面较平；右边投射器开着，同一位置布满细碎亮点](visual-runtime-captures/ir_emitter_pair.png)

### 判断每一帧投射器的开关

本项目的配对节点 [`emitter_pair`](https://github.com/EnosElinsa/wheeltec-ros-source-reference/blob/62aacaed782091b06060ace276c64e9aaf84ae6b/ros2/navigation/vision-nav/wheeltec_vision_nav/wheeltec_vision_nav/emitter_pair_logic.py) 要先知道每一帧投射器是开是关。这台 D435C 随图像发出的元数据里没有投射器状态，配对节点因此直接从图像判断。

判断的依据是散斑留下的孤立亮点。配对节点逐个检查红外图像上的像素，比它上下左右四个相邻像素的平均亮度高出 25 个灰度级以上的像素记为一个亮点，亮点占全部像素的比例称为亮点比例。投射器打开的一帧满是散斑，亮点比例是相邻关闭帧的好几倍。

配对节点把每一帧与前后相邻的帧比较，两帧拍摄时刻相差不超过 $0.05\,\mathrm{s}$ 才算相邻。一帧的亮点比例达到相邻帧的 1.5 倍以上时，这一帧判为打开，相邻帧判为关闭。深度图像的有效像素比例作为第二个依据：投射器打开时有效距离更多，两帧相差超过 8% 时也参与判断。两个依据得出相反的结论，或者差别都不够大，这两帧就不作判断，也不参与配对。下图画出这一过程：亮点比例一高一低交替，每一帧无散斑的红外与紧挨着它、投射器打开的一帧深度配成一对。

![投射器交替与配对。上行为逐帧的红外，中行为亮点比例，相邻两帧之比超过 1.5 才判定开关；下行每一帧投射器关着的红外与相邻一帧投射器开着的深度配成一对](./assets/emitter-pairing.png)

配对节点每秒发布一次状态，写出这一秒收到的红外帧数、配成的对数，以及两种帧亮点比例的中位数。正常时配成的对数约为红外帧数的一半，打开帧的亮点比例约为关闭帧的数倍。

```yaml
# /vision/emitter_pair/status  类型 std_msgs/msg/String，每秒一条，内容为 JSON
data: '{"source": "image",        # 开关状态的来源：image 表示由图像判断
        "ir_frames": 30,           # 这一秒收到的红外帧数
        "paired": 15,              # 这一秒配成的对数
        "dots_off_median": ...,    # 配对所用红外（投射器关）的亮点比例中位数
        "dots_on_median": ...}'    # 配对所用深度那一帧（投射器开）的亮点比例中位数
```

## 1.3 合成一条消息

配对节点判定开关之后，取最新一帧投射器关着的红外，再在 $0.12\,\mathrm{s}$ 内找投射器开着、离它最近的一帧深度。两帧是相邻的两次拍摄，拍摄时刻相差约 $0.033\,\mathrm{s}$，时间戳也不同。

视觉里程计要在同一个像素上同时读到亮度和距离，必须把这两帧当成同一时刻。配对节点因此保留深度图像的距离和像素位置，只把它的时间戳改成这一帧红外的时间戳，然后把两幅图像分别发布到 `/vision/paired/infra1/image_rect_raw` 和 `/vision/paired/depth/image_rect_raw`。每次发出的时间戳都比上一次晚，同一帧红外不会发两次。

RTAB-Map 的同步节点订阅这两路图像，把时间戳相同的一对写进同一条消息。同时带有一幅图像和一幅深度图像的消息称为 **RGB-D**（RGB-Depth）。RGB 原指红、绿、蓝三个颜色通道，这里的图像是投射器关着时拍下的左红外。

```yaml
# /rtabmap/rgbd_image  类型 rtabmap_msgs/msg/RGBDImage，每配成一对发布一条
header:
  stamp: ...                               # 这一帧红外的拍摄时刻
  frame_id: camera_infra1_optical_frame    # 与红外相同
rgb:                                       # 投射器关着时的左红外，亮度
  encoding: "mono8"
  width: 848
  height: 480
depth:                                     # 投射器开着时的深度图像，距离，单位 mm
  encoding: "16UC1"
  width: 848
  height: 480
  frame_id: camera_depth_optical_frame
rgb_camera_info: { ... }                   # 左红外的相机信息
depth_camera_info: { ... }                 # 深度图像的相机信息
```

# 2. 估计相对出发的运动

合成后的 RGB-D 消息在同一个像素上给出亮度和到镜头的距离。这一节先由像素和距离算出镜头前的坐标，再确定相机在车身上的位置，然后由 RTAB-Map 的视觉里程计估计车的运动。底盘另外给出轮速和陀螺仪角速度，最后由 robot_localization 把三份材料融合成一条运动。建图和定位都依赖这条运动。

## 2.1 由像素和距离得到坐标

深度图像里的距离只说明一个点离镜头多远，没有说明它在镜头的左右、上下偏了多少。估计运动要比较前后帧里同一个点的三维坐标，所以要先把像素和距离换成坐标。

以光学中心为原点的坐标系称为**光学坐标系**（Optical Frame）。光学坐标系的 $X_c$ 轴向右，与列号增加的方向相同。$Y_c$ 轴向下，与行号增加的方向相同。$Z_c$ 轴沿镜头正前方，深度图像里的距离就是一个点的 $Z_c$。镜头正前方那条线打在图像上的像素称为**主点**（Principal Point），记为 $(c_x, c_y)$。下图中红线从空间中的点穿过像素 $(u, v)$，回到光学中心。

![小孔模型。原点为光学中心，Xc 向右，Yc 向下，Zc 朝前，视线穿过像素 (u, v)。来源：OpenCV, Camera Calibration and 3D Reconstruction](./assets/opencv-pinhole-camera-model.png)

来源：[OpenCV, Camera Calibration and 3D Reconstruction](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html)。

把坐标换成像素要用到镜头自身的一组固定参数，称为**内参**（Intrinsic Parameters）。测出内参的过程称为**标定**（Calibration），本机出厂时已经完成，内参写在相机信息的字段 `k` 里，排成一个 $3 \times 3$ 矩阵：

$$
K = \begin{bmatrix} f_x & 0 & c_x \\ 0 & f_y & c_y \\ 0 & 0 & 1 \end{bmatrix}.
$$

$f_x$、$f_y$ 是以像素为单位的焦距，与 1.1 视差公式里的焦距是同一个量。本机红外 $f_x = f_y = 421.374$，主点 $(c_x, c_y) = (420.745,\ 239.283)$。

从上往下看，光学中心、空间中的点和它在像平面上的像构成两个相似三角形。大三角形的两条直角边是 $X$ 和 $Z$，小三角形的两条直角边是像素偏离主点的距离 $u - c_x$ 和焦距 $f_x$，因此 $(u - c_x)/f_x = X/Z$。竖直方向同理，于是

$$
u = c_x + f_x\,\frac{X}{Z},
\qquad
v = c_y + f_y\,\frac{Y}{Z}.
$$

![左：主点加上 f_x X/Z 得到列号 u，加上 f_y Y/Z 得到行号 v。右：从上往下看，u − c_x 与 f_x 之比等于 X 与 Z 之比](./assets/pixel-to-xyz.png)

反过来，已知像素 $(u, v)$ 和深度图像里的距离 $Z$，就能算出这个点在光学坐标系里的坐标：

$$
X = \frac{(u - c_x)\,Z}{f_x},
\qquad
Y = \frac{(v - c_y)\,Z}{f_y}.
$$

例如第 631 列、第 276 行的像素，深度图像给出距离 $1.5\,\mathrm{m}$，则 $X = (631 - 420.745) \times 1.5 / 421.374 \approx 0.75\,\mathrm{m}$，$Y = (276 - 239.283) \times 1.5 / 421.374 \approx 0.13\,\mathrm{m}$。算出的点在镜头右方 0.75 m、下方 0.13 m、前方 1.5 m。

## 2.2 相机相对车身的位置和朝向

2.1 的坐标以光学中心为原点，只说明点在镜头的哪个方向，还不能说明它在车的哪个方向。从一个坐标系到另一个坐标系的平移和转动称为**变换**（Transform），把镜头前的点换到车身上，要用车身到镜头的一段变换。

车身坐标系 `base_footprint` 设在车身竖直投影到地面的位置，原点在左右方向的正中，$x$ 轴向前，$y$ 轴向左，$z$ 轴向上。RealSense 驱动把相机的根坐标系命名为 `camera_link`，原点就在左红外的光学中心，坐标轴方向与车身相同。本项目的启动文件在启动时按相机支架的设计图改写车体模型里的相机位置，使 `base_footprint` 到 `camera_link` 的变换为

$$
(t_x, t_y, t_z) = (0.187,\ 0.0175,\ 0.132)\,\mathrm{m},
\qquad
\text{转动} = \text{单位矩阵}.
$$

左红外的光学中心因此在车身原点前方 0.187 m、左方 0.0175 m、地面以上 0.132 m，镜头朝向与车头相同。

`camera_link` 与光学坐标系原点相同，坐标轴方向不同。车身方向是 $x$ 向前、$y$ 向左、$z$ 向上，光学坐标系是 $Z_c$ 向前、$X_c$ 向右、$Y_c$ 向下。RealSense 驱动发布这一段固定的转动，把光学坐标系里的 $(X_c, Y_c, Z_c)$ 换成车身方向上的 $(Z_c,\ -X_c,\ -Y_c)$。2.1 例子里的点在车身方向上就是前方 1.5 m、右方 0.75 m、下方 0.13 m。再加上相机的安装位置，它相对车身原点在前方 $1.687\,\mathrm{m}$、右方 $0.7325\,\mathrm{m}$，离地约 $0.00\,\mathrm{m}$，正是车前方地面上的一个点。

## 2.3 视觉里程计

合成后的 RGB-D 消息在每个像素上同时给出亮度和距离。2.1 的公式把像素和距离换成光学坐标系里的坐标，2.2 给出镜头在车身上的位置。RTAB-Map 的视觉里程计节点订阅这条消息，由前后帧里同一批点的坐标变化推算镜头的转动和平移，再逐帧累加成车相对出发的运动。由图像估计运动的过程称为**视觉里程计**（Visual Odometry, VO）。视觉里程计处理一帧分四步，依次是挑出特征点、描述并匹配特征点、求解这一帧的位姿、发布位姿。

### 特征点

视觉里程计先在当前帧的左红外上挑出下一帧还能认出来的像素。白墙和地面上相邻像素的亮度几乎相同，下一帧里无法确定哪一个是原来那个。与周围像素明显不同的像素才能被认出，这样的像素称为**特征点**（Feature Point）。

判断一个像素能否与周围区分，要以它为中心取一个方形窗口 $W$，把窗口平移一小段 $(\Delta u, \Delta v)$，再比较平移前后窗口内的亮度。记 $I(u, v)$ 为第 $u$ 列、第 $v$ 行像素的亮度。平移前后亮度差的平方和为

$$
E(\Delta u, \Delta v) = \sum_{(u, v) \in W} \big[\, I(u + \Delta u,\ v + \Delta v) - I(u, v) \,\big]^2 .
$$

$E$ 大，说明窗口一平移亮度就改变，窗口中心的像素在下一帧里容易找回。$E$ 接近 0，说明平移后看起来和原来一样，中心像素找不回来。

平移很小时，平移后的亮度可以写成平移前的亮度加上沿两个方向的变化：

$$
I(u + \Delta u,\ v + \Delta v) \approx I(u, v) + I_u\,\Delta u + I_v\,\Delta v .
$$

式中 $I_u = I(u + 1, v) - I(u, v)$ 是与右侧相邻像素的亮度差，$I_v = I(u, v + 1) - I(u, v)$ 是与下方相邻像素的亮度差。只保留一次项的近似称为**一阶泰勒展开**（First-Order Taylor Expansion）。把它代入 $E$ 并展开平方：

$$
E \approx \sum_{W} \big( I_u\,\Delta u + I_v\,\Delta v \big)^2
= \Delta u^2 \sum_{W} I_u^2 + 2\,\Delta u\,\Delta v \sum_{W} I_u I_v + \Delta v^2 \sum_{W} I_v^2 .
$$

右边三项恰好是一个 $2 \times 2$ 矩阵左右各乘一次平移量的结果：

$$
E \approx
\begin{bmatrix} \Delta u & \Delta v \end{bmatrix}
M
\begin{bmatrix} \Delta u \\ \Delta v \end{bmatrix},
\qquad
M = \begin{bmatrix} \sum_W I_u^2 & \sum_W I_u I_v \\ \sum_W I_u I_v & \sum_W I_v^2 \end{bmatrix}.
$$

矩阵 $M$ 只由窗口内的亮度差算出，与平移的方向无关。窗口选定之后，向任何方向平移的 $E$ 都由 $M$ 决定。

沿某个方向平移时，$M$ 给出的变化快慢可以直接算出。取长度为 1 的方向 $\mathbf{w}$，沿它平移 $s$ 个像素，平移量就是 $s\,\mathbf{w}$，代入上式得 $E \approx s^2\,\mathbf{w}^{\mathsf T} M \mathbf{w}$。$\mathbf{w}^{\mathsf T} M \mathbf{w}$ 因此表示沿 $\mathbf{w}$ 每平移一个像素，亮度差的平方和增加多少。$M$ 是对称矩阵，存在两个互相垂直的方向使 $M\mathbf{w} = \lambda\,\mathbf{w}$，沿这两个方向 $\mathbf{w}^{\mathsf T} M \mathbf{w} = \lambda$。沿这两个方向得到的 $\lambda$ 称为 $M$ 的**特征值**（Eigenvalue），较小的记为 $\lambda_1$，较大的记为 $\lambda_2$。其他方向上的 $\mathbf{w}^{\mathsf T} M \mathbf{w}$ 都介于 $\lambda_1$ 与 $\lambda_2$ 之间。

$2 \times 2$ 对称矩阵 $\begin{bmatrix} a & b \\ b & c \end{bmatrix}$ 的两个特征值是

$$
\lambda_{1,2} = \frac{a + c}{2} \mp \sqrt{\Big(\frac{a - c}{2}\Big)^2 + b^2}\, .
$$

以一个具体的窗口为例。设窗口内求和得到 $M = \begin{bmatrix} 5 & 2 \\ 2 & 2 \end{bmatrix}$（亮度差平方的单位从略）。代入公式，$\frac{a + c}{2} = 3.5$，根号内为 $1.5^2 + 2^2 = 6.25$，开方得 $2.5$，于是 $\lambda_1 = 1$，$\lambda_2 = 6$。两个特征值对应的方向是 $\mathbf{w}_1 = (-1, 2)/\sqrt{5}$ 和 $\mathbf{w}_2 = (2, 1)/\sqrt{5}$，代回验算：

$$
\mathbf{w}_2^{\mathsf T} M \mathbf{w}_2 = \frac{1}{5}\,(2,\ 1)\begin{bmatrix} 12 \\ 6 \end{bmatrix} = 6,
\qquad
\mathbf{w}_1^{\mathsf T} M \mathbf{w}_1 = \frac{1}{5}\,(-1,\ 2)\begin{bmatrix} -1 \\ 2 \end{bmatrix} = 1 .
$$

沿 $\mathbf{w}_2$ 平移时亮度变化最快，沿 $\mathbf{w}_1$ 平移时变化最慢。向正右方平移，即 $\mathbf{w} = (1, 0)$，得到 $\mathbf{w}^{\mathsf T} M \mathbf{w} = a = 5$，落在 1 与 6 之间。

要在下一帧里认出一个像素，窗口向哪个方向平移都要引起足够的亮度变化，所以只需看最不利的方向，也就是 $\lambda_1$。$\lambda_1$ 大，任何方向上的变化都不会比它小。一条竖直的亮暗分界是 $\lambda_1$ 为 0 的典型：设 $5 \times 5$ 的窗口里左侧亮度为 50、右侧为 150，每一行只有跨过分界的那一个像素 $I_u = 100$，其余的 $I_u$ 和全部 $I_v$ 都是 0，于是

$$
M = \begin{bmatrix} 5 \times 100^2 & 0 \\ 0 & 0 \end{bmatrix}, \qquad \lambda_1 = 0,\quad \lambda_2 = 5 \times 10^4 .
$$

沿分界上下平移，亮度不变，窗口中心在下一帧里只能确定左右位置，确定不了上下位置。下图把均匀区域、边缘和角点三种窗口放在一起：均匀区域上 $\lambda_1$、$\lambda_2$ 都接近 0，边缘上只有 $\lambda_2$ 较大，角点上两个都较大。

![三种窗口。均匀区域上两个特征值都接近 0，边缘上只有较大的一个不为 0，角点上两个都较大。绿箭头方向上平移亮度不变，红箭头方向上平移亮度改变](./assets/gftt-window-cases.png)

视觉里程计按 $\lambda_1$ 从大到小挑选特征点，这一判据称为**适合跟踪的特征**（Good Features to Track, GFTT）。$\lambda_1$ 小于整幅图像最大值的千分之一的像素不选，两个特征点之间至少相隔 7 个像素，每帧最多保留 1500 个。距离不在 $0.20$～$3.5\,\mathrm{m}$ 内的像素也不选：太近时深度图像里没有有效距离，太远时距离的误差过大。下图是实机一帧左红外上挑出的特征点。红点落在背包、饮水机和柜子的棱角上，地面和窗帘上亮度均匀的区域没有红点，与上面三种窗口的判断一致。

![特征点。红点标在左红外上，落在物体的棱角处](visual-runtime-captures/vo_features.png)

### 描述与匹配

视觉里程计接着要为当前帧的每个特征点找出它在前几帧里对应的那个特征点。特征点本身只是一个像素位置，要在另一帧里认出它，还要记下它周围的亮度是什么样子。视觉里程计用的记法称为**二进制鲁棒独立基本特征**（Binary Robust Independent Elementary Features, BRIEF），过程分取样、编码、比较、选最近四步。

取样时，视觉里程计先把图像稍加平滑，减小单个像素的噪声，再以特征点为中心取一个 $48 \times 48$ 像素的方块，按一张固定的表在方块内取 256 对像素位置 $(p_i, q_i)$，$i = 1, \dots, 256$。这张表对所有特征点、所有帧都相同，两个特征点的第 $i$ 位因此总是在同样的相对位置上取得。

编码时，每一对像素比较一次亮度：$I(p_i) < I(q_i)$ 记为 1，否则记为 0。256 对比较得到一串 256 位的 0 和 1，称为这个特征点的**描述子**（Descriptor）。描述子只记录两个像素谁亮谁暗，不记录亮度本身，所以整幅图像一起变亮或变暗时，描述子保持不变。

比较两个描述子时逐位对照，取值不同的位数称为**汉明距离**（Hamming Distance）。汉明距离越小，两个特征点周围的亮暗关系越接近。

选最近时，当前特征点与候选特征点逐一计算汉明距离，取距离最小的那个作为同一个点。最小距离还要明显小于第二小的距离，不超过它的 0.8 倍，否则说明有两个候选看起来差不多，这个特征点不参与匹配。下图用 8 对像素代替 256 对，走一遍这四步：左边是特征点周围取的 8 对像素，中间是逐对比较得到的 8 位描述子，右边与两个候选逐位对照，候选 A 只差 1 位，候选 B 差 7 位，于是取候选 A。

![描述与匹配。左：特征点周围按固定的表取 8 对像素。中：每对比较亮度得到 0 或 1。右：与候选逐位对照，不同的位数最少的候选 A 是同一个点](./assets/brief-descriptor.png)

候选特征点来自视觉里程计保存的局部特征表。表里是最近几个关键帧上的特征点和它们的描述子，关键帧指特征点被补进这张表的帧。视觉里程计对这一帧的运动已有预测时，先按预测把表中每个点投影到当前图像上，只在投影位置周围 40 个像素内寻找候选。这样既减少了比较次数，也避免把远处一个长得相似的角点错认成同一个点。匹配的结果是若干对对应，每一对由当前帧上的一个像素 $(u, v)$ 和表中的一个特征点组成。

### 求解位姿

匹配完成后，视觉里程计由这些对应求出当前镜头的位置和朝向。镜头或车身的位置和朝向合称**位姿**（Pose）。

已知的量有两类。第一类是表中特征点在出发坐标系里的坐标，记为 $\mathbf{x}$。每个特征点被补进表时，视觉里程计已经用 2.1 的公式由它的像素和距离算出光学坐标系里的坐标，再用当时那一帧的位姿换到出发坐标系。第二类是当前帧上与它匹配的像素 $(u, v)$。

待求的是当前镜头的位姿，写成一个转动矩阵 $R$ 和一个平移向量 $\mathbf{t}$。$R$ 是 $3 \times 3$ 矩阵，$\mathbf{t}$ 是三个数，单位 m。两者合起来把出发坐标系里的点换到当前镜头前。

对每一对匹配，先用待求的 $R$、$\mathbf{t}$ 把 $\mathbf{x}$ 换成当前镜头前的坐标，再按 2.1 的公式投影到像素：

$$
\begin{bmatrix} X_c \\ Y_c \\ Z_c \end{bmatrix} = R\,\mathbf{x} + \mathbf{t},
\qquad
\hat u = c_x + f_x \frac{X_c}{Z_c},
\qquad
\hat v = c_y + f_y \frac{Y_c}{Z_c}.
$$

投影得到的 $(\hat u, \hat v)$ 与当前帧上实际匹配到的 $(u, v)$ 之差称为**重投影误差**（Reprojection Error）：

$$
e = \sqrt{(u - \hat u)^2 + (v - \hat v)^2}\, .
$$

$R$、$\mathbf{t}$ 取得正确时，每一对的重投影误差都接近 0。视觉里程计从预测的位姿出发反复调整 $R$、$\mathbf{t}$，使全部匹配的重投影误差平方和最小，得到的 $R$、$\mathbf{t}$ 就是这一帧的位姿。已知若干个点的空间坐标和它们在图像上的像素、反求相机位姿的问题称为**透视 n 点问题**（Perspective-n-Point, PnP）。下图在像平面上画出求解前后：红圈是当前帧上匹配到的特征点，蓝点是 $\mathbf{x}$ 按 $R$、$\mathbf{t}$ 投影得到的像素。求解前蓝点与红圈分开，虚线的长度就是重投影误差。求解后蓝点落在红圈上。

![重投影。求解前投影（蓝点）与当前帧的特征点（红圈）分开，虚线为重投影误差。求解后投影落在特征点上](./assets/vo-reprojection.png)

匹配里难免混有错配，一对错配就能把平方和最小的解拉偏。视觉里程计因此先随机取几对匹配算出一组 $R$、$\mathbf{t}$，再统计全部匹配中重投影误差不超过 2 个像素的有多少对，这些匹配称为**内点**（Inlier）。随机取样最多重复 300 次，取内点最多的那一组，最后只用这组的内点重新求解。先随机取样、再按一致的数量挑选的做法称为**随机抽样一致**（Random Sample Consensus, RANSAC）。

内点不少于 10 个时，视觉里程计采用这个位姿。内点不足 10 个，说明当前帧与局部特征表对不上，这一帧判为**跟丢**（Lost），不给出位姿。

### 发布位姿

视觉里程计求出的位姿是镜头相对出发时镜头的运动。发布前，它用 2.2 的镜头安装位置把这段运动换算成车身坐标系 `base_footprint` 相对出发处的运动，称为视觉位姿。出发处的坐标系名为 `odom`，就是车刚启动时 `base_footprint` 所在的位置和朝向。视觉位姿连同车身的速度一起发布在 `/odom_vo`，供 2.5 的运动融合使用。

朝向用**四元数**（Quaternion）表示，四个数 $(x, y, z, w)$ 合起来描述一次转动。车在地面上绕竖直轴转过角 $\theta$ 时，四元数是 $\big(0,\ 0,\ \sin\tfrac{\theta}{2},\ \cos\tfrac{\theta}{2}\big)$。不转时是 $(0, 0, 0, 1)$，向左转 $90^\circ$ 时是 $(0, 0, 0.707, 0.707)$。

```yaml
# /odom_vo  类型 nav_msgs/msg/Odometry，视觉里程计每处理完一帧发布一条
header:
  stamp: ...                    # 这一帧红外的拍摄时刻
  frame_id: odom                # 位姿相对的坐标系：出发处
child_frame_id: base_footprint  # 被描述的坐标系：车身
pose:
  pose:
    position: { x: ..., y: ..., z: ... }              # 车身位置，单位 m
    orientation: { x: ..., y: ..., z: ..., w: ... }   # 车身朝向，四元数
  covariance: [ ... ]           # 位姿的方差，6 × 6 共 36 个数
twist:
  twist:
    linear: { x: ..., y: ..., z: ... }    # 车身坐标系下的速度，单位 m/s
    angular: { x: ..., y: ..., z: ... }   # 绕三个轴转动的角速度，单位 rad/s
  covariance: [ ... ]           # 速度的方差
```

每一帧的内点数和是否跟丢另外发布在 `/odom_info_lite`，7.3 的看门狗读取它判断视觉是否可靠。跟丢的那一帧，`/odom_vo` 仍然发出一条消息，但四元数的四个数全为 0，方差填成很大的数，表示这一帧没有可用的位姿。

```yaml
# /odom_info_lite  类型 rtabmap_msgs/msg/OdomInfo，与 /odom_vo 同步发布，下面只列两个字段
lost: false        # 这一帧是否跟丢
inliers: ...       # 这一帧的内点数，少于 10 时 lost 为 true
```

## 2.4 轮速与陀螺仪

视觉里程计给出的运动全部来自图像，特征点不足或镜头被遮挡时就会跟丢。WHEELTEC 的底盘节点另外从底盘控制板读回车速和陀螺仪数据，本项目的输入整理节点再把其中的陀螺仪零偏扣除，为 2.5 的融合准备好材料。

### 轮速位姿

底盘控制板由车轮上的[编码器](../02-hardware-basics/08-sensors-and-feedback.md#encoder)测出车轮转速，换算成车的前进速度 $v_x$。这台车前轮转向，转动快慢由前进速度和前轮转角按阿克曼转向的[底盘运动模型](../02-hardware-basics/09-chassis-motion-control.md#body-coordinate)算出。底盘节点把速度随时间累加，得到车相对上电处的位置和朝向，称为轮速位姿，连同速度一起发布在 `/wheel/odom`。

轮速位姿的可信程度随车的状态变化，底盘节点把它写进方差。车在行驶时，前进速度的方差为 $10^{-3}$，由转角算出的转动快慢方差为 $10^{3}$，表示这个量几乎不可信：转角的零位偏差和车轮打滑都会直接变成朝向误差。车停着时，所有速度都是 0，方差降到 $10^{-9}$，表示车确实没有动。

```yaml
# /wheel/odom  类型 nav_msgs/msg/Odometry，底盘节点发布，每次读回底盘数据发布一条
header:
  frame_id: wheel_odom            # 位姿相对的坐标系：上电时车身所在处
child_frame_id: base_footprint    # 被描述的坐标系：车身
pose:
  pose: { ... }                   # 轮速位姿
twist:
  twist:
    linear: { x: ..., y: 0.0 }    # 前进速度，单位 m/s，前轮转向车没有横向速度
    angular: { z: ... }           # 由前轮转角算出的转动快慢，单位 rad/s
  covariance: [ ... ]             # 行驶时 x、y 方向为 1e-3，转动为 1e3；停车时全部为 1e-9
```

### 陀螺仪角速度

底盘控制板上的 [IMU](../02-hardware-basics/08-sensors-and-feedback.md#imu) 含有陀螺仪，直接测出车绕竖直轴转动的快慢。底盘节点把它发布在 `/imu/data_raw`，字段 `angular_velocity.z` 就是这个角速度，单位 rad/s，自报的方差为 $10^{-6}$。

陀螺仪在车静止时的读数并不为 0，而是一个几乎不变的小值，这个值称为**零偏**（Bias）。本机陀螺仪的零偏约为 $8 \times 10^{-4}\,\mathrm{rad/s}$。把它当成真实的转动累加起来，10 分钟后朝向就偏了 $8 \times 10^{-4} \times 600 = 0.48\,\mathrm{rad}$，约 $27^\circ$。

本项目的输入整理节点 [`ekf_inputs`](https://github.com/EnosElinsa/wheeltec-ros-source-reference/blob/62aacaed782091b06060ace276c64e9aaf84ae6b/ros2/navigation/vision-nav/wheeltec_vision_nav/wheeltec_vision_nav/ekf_inputs_logic.py) 利用轮速判断车是否静止，并在静止时估计零偏。轮速里的前进速度和转动快慢都小于 $0.001$ 并且持续 $0.5\,\mathrm{s}$ 以上时，车判为静止。静止期间每收到一个陀螺仪读数 $g$，零偏估计 $b$ 就向它靠近一小步：

$$
b \leftarrow b + 0.02\,(g - b).
$$

一步只移动差值的 2%，单个读数的噪声不会让 $b$ 跳动。车一开动，$b$ 保持不变。输入整理节点把扣除零偏后的 $g - b$ 发布在 `/vision/imu`，方差改为 $10^{-5}$，称为陀螺仪角速度。方差比原来大，是因为扣除零偏之后仍留有温度变化带来的残差。

### 视觉位姿的两处调整

底盘启动后，RTAB-Map 的视觉里程计用轮速位姿在两帧之间的变化作为 2.3 里对这一帧运动的预测，匹配时只在预测位置周围寻找候选。某一帧跟丢后，下一帧从当时的轮速位姿重新开始，视觉位姿因此不会跳回出发处。

视觉里程计自报的速度方差只有 $10^{-7}$ 量级，相当于速度误差只有 $0.0003\,\mathrm{m/s}$，远小于实际误差。按这个方差融合，一帧误配就能压过轮速和陀螺仪。输入整理节点因此把视觉速度的方差抬到下限：前进和横向速度不小于 $2.5 \times 10^{-3}$，对应标准差 $0.05\,\mathrm{m/s}$，转动快慢不小于 $10^{-3}$，对应标准差约 $0.03\,\mathrm{rad/s}$。调整后的视觉位姿发布在 `/vision/odom_vo`，其他内容与 `/odom_vo` 相同。

## 2.5 融合一条运动

轮速位姿、陀螺仪角速度和视觉位姿各有长处。robot_localization 的 [EKF](30-odometry-tf-time.md#odometry-ekf) 节点把三者融合成一条运动，称为融合后的运动，建图、定位和控制都订阅这一条。

### 融合的做法

EKF 节点维护车在平面上的一组状态：位置 $x$、$y$，朝向 $\theta$，前进速度 $v_x$、横向速度 $v_y$ 和转动快慢 $\omega$，每个量都附有方差，表示当前估计的可信程度。每一步先做预测，按当前速度把位置和朝向向前推进一小段时间，推进后方差变大。然后做更新，每收到一个测量，就把相应的估计向测量值拉近。

对单独一个量，更新写成

$$
\hat{s} \leftarrow \hat{s} + K\,(z - \hat{s}),
\qquad
K = \frac{P}{P + R},
\qquad
P \leftarrow (1 - K)\,P .
$$

式中 $\hat{s}$ 是当前估计，$P$ 是它的方差，$z$ 是测量值，$R$ 是测量的方差。测量越可信，$R$ 越小，$K$ 越接近 1，估计就越靠近测量。以转动快慢为例，设估计的方差 $P = 10^{-4}$。陀螺仪角速度 $R = 10^{-5}$，$K \approx 0.91$，估计几乎跟随陀螺仪。行驶中轮速给出的转动快慢 $R = 10^{3}$，$K \approx 10^{-7}$，几乎不起作用。停车时轮速的 $R = 10^{-9}$，$K \approx 1$，转动快慢回到 0。

三份材料各自提供的量如下表。

| 材料 | 融合的量 | 方差 |
| --- | --- | --- |
| 轮速位姿 `/wheel/odom` | $v_x$、$v_y$、$\omega$ | 行驶时 $v_x$、$v_y$ 为 $10^{-3}$，$\omega$ 为 $10^{3}$，停车时全部为 $10^{-9}$ |
| 陀螺仪角速度 `/vision/imu` | $\omega$ | $10^{-5}$ |
| 视觉位姿 `/vision/odom_vo` | $v_x$、$\omega$ | 不小于 $2.5 \times 10^{-3}$ 和 $10^{-3}$ |

三份材料只提供速度，位置和朝向由 EKF 节点自己累加，所以任何一份材料重新从零开始都不会让融合后的运动跳变。视觉位姿还要先过一道检查：一个测量与当前估计之差超过两者合起来的 3 倍标准差时，EKF 节点丢弃这个测量。这种以标准差为单位衡量的差称为**马氏距离**（Mahalanobis Distance）。一帧匹配错误的视觉位姿因此不会拉偏融合后的运动。

### 发布融合后的运动

EKF 节点把融合后的运动发布在 `/odom`，同时把同一位姿作为 `odom` 到 `base_footprint` 的变换发出，这一段变换在第 3 节接入坐标系树。

```yaml
# /odom  类型 nav_msgs/msg/Odometry，EKF 节点发布，融合后的运动
header:
  stamp: ...
  frame_id: odom                 # 出发处
child_frame_id: base_footprint   # 车身
pose:
  pose:
    position: { x: ..., y: ..., z: 0.0 }       # 平面上的位置，单位 m，高度固定为 0
    orientation: { x: 0.0, y: 0.0, z: ..., w: ... }   # 只绕竖直轴转动
  covariance: [ ... ]            # 相对出发处的累计不确定程度，随行驶时间增大
twist:
  twist: { ... }                 # 融合后的速度
```

底盘不启动时没有轮速和陀螺仪，例如建图时由人推车。此时本项目的 `hold_odom_tf` 节点代替 EKF 节点，把视觉位姿直接发布到 `/odom` 和同一段变换。视觉跟丢的那一帧，它在这一帧的时间戳上重复上一个有效位姿。视觉里程计重新从零开始、位姿相对上一帧跳过 1 m 或 1 rad 时，它把新的起点接在上一个位姿之后，`/odom` 不跳回出发处。

融合后的运动以本次出发处为原点，只说明车相对出发处走了多远、转了多少。融合后的运动与镜头、场地之间的关系由第 3 节接起来。

# 3. 连接图像、车体与场地

第 2 节交出了两类量：镜头前的点坐标在光学坐标系里，融合后的运动是 `base_footprint` 相对 `odom` 的位姿。建图要把每一帧看到的点放到同一张场地的图上，规划路径要知道车在场地上的位置，两件事都要把不同坐标系里的量换到同一个坐标系。这一节先说明 ROS 2 保存和串接变换的机制，再区分车身、出发处和场地三个坐标系，最后写明每一段变换由谁发布。

## 3.1 坐标变换

一个点从光学坐标系换到场地，要依次经过相机、车身和出发处，相邻两个坐标系之间各有一段变换，而且各段来自不同的节点。ROS 2 用 [TF](../05-ros2-development/26-tf-urdf-rviz.md#model-tf-rviz) 把这些带名字的变换收在一起。每段变换写明父坐标系和子坐标系的名字，以及子坐标系相对父坐标系的平移和转动，本章写成“父→子”。查询时给出两端的名字，TF 把中间各段依次接上，得到一端相对另一端的平移和转动，查询的程序不必知道每一段由谁发布。随时间变化的变换发布在 `/tf`，安装之后不再改变的变换发布在 `/tf_static`，消息类型都是 `tf2_msgs/msg/TFMessage`。

## 3.2 车身、出发处与场地

`odom→base_footprint` 就是 2.5 发布的融合后的运动。这段运动由一段段速度累加而来，每一段都带误差，走得越远，`odom` 里算出的位置偏离实际位置越多，这段偏差称为累计误差。

场地上另设坐标系 `map`，固连在环境上。车在 `map` 里的位置由第 4 节的建图和第 5 节的定位给出。修正不直接写进 `odom→base_footprint`：每次修正都改这一段，车的位置会随修正跳变，按路径控制速度的程序读到的运动就不再平滑。修正另记为一段 `map→odom`。`odom→base_footprint` 保持平滑的累计运动，`map→odom` 记录出发处相对场地的偏差，两段接起来才是车在场地上的位置。

下图把两段分开画。左图只有 `odom→base_footprint`，蓝色路程从出发处开始累加，末端的蓝框偏离了灰色虚框表示的实际位置。右图加上 `map→odom`，整个 `odom` 坐标系平移并转动，蓝框落回实际位置，而路程本身没有改变。

![左图只用 odom→base_footprint，按 /odom 算出的车身位置偏离实际位置；右图加上 map→odom，odom 坐标系整体平移并转动，车身位置与实际位置重合](./assets/map-odom-correction.png)

三个坐标系的固连对象和含义如下表。

| 名称 | 固连对象 | 含义 |
| --- | --- | --- |
| `map` | 环境 | 车在环境中的位置，由建图和定位修正 |
| `odom` | 本次出发时车身所在处 | 相对出发处累计的运动，平滑但带累计误差 |
| `base_footprint` | 车身在地面上的投影 | 车身坐标系，$x$ 向前、$y$ 向左、$z$ 向上 |

## 3.3 变换的发布

从 `map` 到镜头的各段变换由不同的节点发布，下表按从场地到镜头的顺序列出。

| 段 | 发布者 | 话题 |
| --- | --- | --- |
| `map→odom` | RTAB-Map | `/tf` |
| `odom→base_footprint` | robot_localization 的 EKF 节点。底盘不启动时由本项目的 `hold_odom_tf` 发布 | `/tf` |
| `base_footprint→base_link` | 静态变换发布器 | `/tf_static` |
| `base_link→camera_link` | robot_state_publisher，按启动时改写过的车体模型 | `/tf_static` |
| `camera_link→` 光学坐标系 | RealSense 驱动 | `/tf` |
| `base_footprint→wheel_odom` | 本项目的 `wheel_odom_tf`（底盘启动时） | `/tf` |

下图把这些坐标系连成一棵树。箭头从父坐标系指向子坐标系，箭头旁的方框写出发布这一段的节点，粗框浅底的是本项目编写的节点。

![坐标系树。从 map、odom、base_footprint 到相机的光学坐标系，以及挂在 base_footprint 下的 wheel_odom。方框中为发布者](diagrams/tf-tree.svg)

`map→odom` 由 RTAB-Map 在处理第一帧之后开始发布，之后每次回环或定位修正时更新，第 4 节写它怎样得到修正量。`odom→base_footprint` 与 `/odom` 是同一个位姿，时间戳也相同。

`base_footprint→base_link` 与 `base_link→camera_link` 描述车体本身。`base_link` 是车体主连杆上的坐标系，相对 `base_footprint` 有一个固定高度，由出厂的车型配置给出。车体各连杆之间的位置写在 [URDF](../05-ros2-development/26-tf-urdf-rviz.md#model-tf-rviz) 车体模型里，由 robot_state_publisher 发布。

出厂模型里的相机位置是早先装在车上的另一台相机，(https://github.com/EnosElinsa/wheeltec-ros-source-reference/blob/62aacaed782091b06060ace276c64e9aaf84ae6b/ros2/navigation/vision-nav/wheeltec_vision_nav/wheeltec_vision_nav/launch_utils.py) 在启动时把它改成 2.2 的 D435C 位置。经 TF 串接后，`base_footprint` 到 `camera_link` 的变换为：

```yaml
# 由 TF 查询 base_footprint→camera_link 得到的变换
header:
  frame_id: base_footprint
child_frame_id: camera_link
transform:
  translation: { x: 0.187, y: 0.0175, z: 0.132 }   # 前方 0.187 m、左方 0.0175 m、离地 0.132 m
  rotation: { x: 0.0, y: 0.0, z: 0.0, w: 1.0 }     # 不转动，镜头朝向与车头相同
```

`camera_link→` 光学坐标系是 2.2 所说的固定转动，由 RealSense 驱动发布，没有平移。

`base_footprint→wheel_odom` 是反过来发布的一段。`/wheel/odom` 写的是 `base_footprint` 相对 `wheel_odom` 的位姿，照原样发布就成了 `wheel_odom→base_footprint`，`base_footprint` 就会同时有 `odom` 和 `wheel_odom` 两个父坐标系，而 TF 里每个坐标系只能有一个父坐标系。本项目的 `wheel_odom_tf` 节点因此把这个位姿求逆，发成 `base_footprint→wheel_odom`。查询 `wheel_odom` 到 `base_footprint` 时，TF 把逆变换再反过来，得到的仍是轮速位姿，2.4 里视觉里程计的预测就是这样取得的。

至此，任一时刻由 TF 都能查出光学坐标系到 `map` 的整段变换。第 4 节用它把每一帧看到的点放到场地上。

# 4. 建立地图

镜头前的点已经能经 TF 换到 `map`，车相对出发处的运动在 `/odom` 上。这一节由 RTAB-Map 把沿途的图像和位姿写成地点记录存入数据库，由每条记录的距离得到占用栅格，再在车回到旧地点时用回环修正位置。边确定位置边建立地图的过程就是 [SLAM](30-odometry-tf-time.md#odometry-slam)。本车用的建图软件称为**实时外观建图**（Real-Time Appearance-Based Mapping, RTAB-Map），“外观”指它靠图像看起来是否相同来认出旧地点。定位时还要用这里留下的数据库和占用栅格。

## 4.1 地点记录与数据库

RTAB-Map 订阅 `/rtabmap/rgbd_image`，每秒最多处理 2 帧。每处理一帧，它先由 TF 查出这帧拍摄时刻 `base_footprint` 相对 `odom` 的位姿。相对上一条记录平移不足 $0.05\,\mathrm{m}$ 并且转动不足 $0.05\,\mathrm{rad}$ 时，这帧不写入。超过其中一项，RTAB-Map 就把这帧的红外图像、深度图像、特征点及其描述子，连同这帧的位姿写成一条记录。RTAB-Map 内部把这样的记录称为 node，与 ROS 2 的节点不是一回事，本章称为地点记录。

每写入一条地点记录，RTAB-Map 还在它与上一条记录之间存下由里程计得到的相对位姿，作为两条记录之间的一条约束。这条约束带有固定的方差：平移 $0.0005\,\mathrm{m^2}$，转动 $0.0005\,\mathrm{rad^2}$，相当于两条相邻记录之间的位置误差约 $0.022\,\mathrm{m}$、朝向误差约 $1.3^\circ$。固定方差不取 `/odom` 里的方差，是因为 `/odom` 的方差描述的是相对出发处的累计不确定程度，会越来越大，而这里需要的是相邻两条记录之间的误差。4.3 会说明这个方差为什么决定了错误回环能否被识别出来。

地点记录写入磁盘上的数据库文件，扩展名为 `.db`。进程退出后文件仍保留，第 5 节定位时读取的就是它。

## 4.2 由距离得到占用栅格

规划路径要知道地面上哪些格子能通行，深度图像给出的却是前方每个像素的距离。RTAB-Map 每写入一条地点记录，就把这帧深度图像投到俯视的格子上。

投影分三步。第一步，由 2.1 的公式把每个像素和距离换成光学坐标系里的点，再经 TF 换到 `base_footprint`。距离不在 $0.20$～$3.5\,\mathrm{m}$ 内的点不用，落在车身本身所占的 $0.5\,\mathrm{m} \times 0.4\,\mathrm{m} \times 0.3\,\mathrm{m}$ 空间里的点也去掉，以免把自己的车头当成障碍。

第二步按表面朝向和高度给点归类。一个点所在的小块表面朝上，即表面法线与竖直方向的夹角不超过 $30^\circ$，并且高度在 $-0.10$～$0.10\,\mathrm{m}$ 之间，这个点记为地面，落到的格子记为空闲。其余高度在 $0.10$～$1.80\,\mathrm{m}$ 之间的点记为障碍，格子记为占用。高于 $1.80\,\mathrm{m}$ 的点是灯或天花板，不记。

第三步补上视线经过的格子。相机到每个地面点或障碍点之间，视线经过的格子也记为空闲，因为视线能到达说明中途没有障碍。半径 $0.05\,\mathrm{m}$ 内不足 3 个邻点的孤立点当作噪声去掉。

下图从侧面看这一归类。贴地的一层是地面，往上到 1.80 m 是障碍，再高的不记，相机到障碍之间的地面格子标为空闲。

![侧视：地面附近为空闲，0.10～1.80 m 为障碍，高于 1.80 m 不记。只用 0.20～3.5 m 内的点，视线经过的格子记为空闲](./assets/depth-to-grid-side.png)

每条记录由此得到一张边长 $0.05\,\mathrm{m}$ 的局部俯视格子，位置以这条记录的位姿为准。RTAB-Map 把所有记录的局部格子按各自在 `map` 中的位姿拼在一起，得到整张**占用栅格**（Occupancy Grid）。拼接时再做两处清理：单独一格、四周都不占用的占用格被去掉，每条记录位姿周围 $0.25\,\mathrm{m}$ 内的格子标为空闲，因为车当时就停在那里。占用栅格发布在 `/map`。

```yaml
# /map  类型 nav_msgs/msg/OccupancyGrid，RTAB-Map 发布，地图更新时发一条
header:
  frame_id: map
info:
  resolution: 0.05        # 格子边长，单位 m
  width: ...              # 列数，沿 x 方向
  height: ...             # 行数，沿 y 方向
  origin: { position: { x: ..., y: ... } }   # 格子 (0, 0) 左下角在 map 中的位置
data: [ ... ]             # 每格一个数：0 空闲，100 占用，-1 未知
```

`data` 按行存放，从格子 $(0, 0)$ 起沿 $x$ 方向写完一行 `width` 个格子，再增加 $y$。图像像素的 $(0, 0)$ 在左上角、行号向下，栅格的 $(0, 0)$ 在左下角、$y$ 向上，两种约定相反。一张 4 列 3 行的栅格与它的 `data` 如下：

```text
y 向上
2 |  -1    0   100    0
1 |   0    0   100    0
0 |   0    0     0    0
    +----+----+-----+----→ x
data: [0, 0, 0, 0,  0, 0, 100, 0,  -1, 0, 100, 0]
```

## 4.3 回环

`/odom` 上的运动带累计误差。车绕场地一圈回到出发处时，按 `/odom` 算出的位置已经偏离出发处，照这个位置拼接局部格子，同一堵墙会在栅格上出现两次。RTAB-Map 在车回到已经写入的地点时，认出当前红外图像与那条地点记录看起来相同，在两条记录之间加一条新的约束，这一次识别称为**回环**（Loop Closure）。

### 识别旧地点

RTAB-Map 为识别另取每帧最多 500 个特征点，把它们的描述子归入一本逐渐扩充的词典，词典里的每一项称为一个视觉单词。每条地点记录由此变成一组单词。当前帧的单词与库中各条记录比较，共有的单词越多，那条记录越可能是同一地点。最可能的那条记录的可能性超过阈值 $0.11$ 时，RTAB-Map 再用 2.3 求位姿的方法在两帧之间求出相对位姿，内点不少于 20 个才把它作为回环约束加入。除按图像识别之外，RTAB-Map 还把按里程计判断在空间上靠近、时间上相隔较久的记录直接拿来求相对位姿，得到的约束称为近邻约束。

下图两帧红外取自同一处、不同时刻的两条地点记录。两帧看起来相同，回环才在它们之间加入约束。

![回环。两帧是同一地点、不同时刻的图像，看起来相同才接受这次回环](visual-runtime-captures/loop_pair.png)

### 图优化与错误回环

全部地点记录和它们之间的约束构成**位姿图**（Pose Graph）：每条记录是一个位姿，每条约束是一段相对位姿，并带有方差。加入回环约束后，RTAB-Map 重新求解全部位姿，使各条约束的偏差除以各自标准差后的平方和最小，这一步称为图优化。本车在平面上求解，只调整前后、左右和朝向。

回环也可能认错。重复的桌椅、相同的柜门都会让两处不同的地方看起来相同。RTAB-Map 在优化后检查每条约束：偏差超过它自身 3 倍标准差的约束说明这次回环与其余约束矛盾，这次回环被拒绝，位姿退回优化前。

这项检查是否有效，取决于里程计约束的方差。下图左边是里程计约束几乎不约束朝向的情形：若直接采用底盘上报的朝向方差 $10^{3}\,\mathrm{rad^2}$，标准差约 $32\,\mathrm{rad}$，任何朝向变化都只算很小的偏差。一条把记录 2 和记录 7 错认成同一处的回环，就能把中间一段路程拧成一圈，而每条约束的偏差仍在 3 倍标准差以内，错误回环因此被接受，地图随之扭曲。右边是 4.1 的固定方差：朝向标准差约 $1.3^\circ$，要把路程拧成一圈，里程计约束的偏差会远超 3 倍标准差，这条回环就被拒绝。

![位姿图与错误回环。左：里程计约束几乎不约束朝向，一条错误回环把中间一段拧成一圈。右：里程计约束带有合理的朝向方差，错误回环的偏差超过 3σ，被拒绝](./assets/pose-graph-constraint.png)

回环被接受后，全部地点记录的位姿更新，占用栅格按新位姿重新拼接。当前记录优化后的位姿与 `/odom` 上位姿之差写成 `map→odom` 发布，所以回环被接受时 `map→odom` 会跳变，而 `odom→base_footprint` 不受影响，这正是 3.2 把修正另记一段的原因。

下图把优化后的地点记录画在 `/map` 上。蓝线按时间先后把记录连起来，是车走过的路程。红线连接相隔很久又看到的同一地点，就是回环约束。绿点为第一条记录，橙箭头为最后一条记录的位置和朝向。

![地点记录的位姿。蓝线为按时间先后的路程，红线为回环约束](visual-runtime-captures/map_nodes.png)

# 5. 在已有地图上定位

建图留下了地点数据库。定位时，相机、配对、合成、视觉里程计和运动融合照常运行，RTAB-Map 读取同一个数据库，把库中全部地点记录载入内存，但不再写入新记录。占用栅格由库中的记录重新拼出并发布在 `/map`，与建图结束时相同。规划路径用的就是定位得到的位姿和这张 `/map`。

定位做的是 4.3 的识别，只是比较对象换成库中全部记录。RTAB-Map 认出当前图像对应的记录，并用 2.3 的方法求出两者之间的相对位姿后，那条记录在 `map` 中的位姿加上这段相对位姿，就是车此刻在 `map` 中的位姿。车在 `map` 中的位姿与 `/odom` 上位姿之差写成 `map→odom` 发布。两次识别之间，车的位置由 `odom→base_footprint` 的累计运动推进。长时间识别不出时，`map→odom` 停留在上一次的值，车在地图上的位置随累计误差偏离。库中没有这一处的记录，识别就没有对象，定位不会给出位置。

下图是定位时相机正在看到的左红外，以及画在已有 `/map` 上的车体。识别得到的车身位置和朝向用橙箭头表示，蓝框是车身在地面上的投影，蓝线是建图时记录连成的路程，用来对照当前位置落在原路程的哪一段。

![当前左红外。定位时用它与库中记录比较](visual-runtime-captures/livecap_infra1_000.png)

![定位得到的位姿。橙箭头为车在已有地图上的位置和朝向，蓝框为车身投影，蓝线为建图时的路程](visual-runtime-captures/localization_pose.png)

刚启动或车被搬动后，识别可能一时找不到对应的记录。此时可以在 RViz 上用 2D Pose Estimate 指出车的大致位置和朝向，RTAB-Map 以它作为 `map→odom` 的初值，之后的识别再修正。

```yaml
# /initialpose  类型 geometry_msgs/msg/PoseWithCovarianceStamped，由 RViz 的 2D Pose Estimate 发布
header:
  frame_id: map
pose:
  pose:
    position: { x: ..., y: ..., z: 0.0 }             # 车在地图上的大致位置
    orientation: { x: 0.0, y: 0.0, z: ..., w: ... }  # 车头的大致朝向
```

# 6. 规划到目标的路径

车在地图上的位姿和占用栅格已经有了。这一节由 Nav2 先把占用栅格和相机刚看到的障碍做成代价地图，再在代价地图上计算到目标点的路径。第 7 节按这条路径控制速度。

## 6.1 代价地图

占用栅格只区分格子本身是否被占用，而车有宽度：车身中心走在紧贴障碍的空闲格上，车身边缘仍会碰到障碍。Nav2 因此在每个占用格周围标出一圈代价逐渐降低的区域，离障碍越近代价越高，规划和控制都避开高代价的格子。这样得到的图称为**代价地图**（Costmap），占用格周围标出的这一圈称为**膨胀**（Inflation）。车身的形状由**足迹**（Footprint）给出，足迹是车身在地面上的多边形，顶点以 `base_footprint` 为原点，单位 m：

```text
[[-0.09, -0.185], [-0.09, 0.185], [0.40, 0.185], [0.40, -0.185]]
```

即车身宽 $0.37\,\mathrm{m}$，从原点向后 $0.09\,\mathrm{m}$、向前 $0.40\,\mathrm{m}$。

Nav2 按本项目启动时生成的参数建立两张代价地图。全局代价地图覆盖整张 `/map`，坐标系为 `map`，格子边长 $0.05\,\mathrm{m}$，膨胀半径 $0.25\,\mathrm{m}$，用来规划整条路径。相机建出的地图在墙边常留下未知格，全局代价地图保留这些未知格，规划时允许路径穿过它们，否则路径常因一小片未知而被堵死。

局部代价地图只覆盖车周围 $3\,\mathrm{m} \times 3\,\mathrm{m}$，坐标系为 `odom`，随车移动，膨胀半径同样为 $0.25\,\mathrm{m}$，用来控制速度。局部代价地图用 `odom` 而不用 `map`，是因为 `map→odom` 在回环和定位修正时会跳变，控制速度要的是平滑的运动。局部代价地图不读 `/map`，只放相机当前看到的障碍，这些障碍由 RTAB-Map 工具包里的两个节点从配对后的深度图像直接算出。

第一个节点把每一帧配对后的深度图像每隔 4 个像素取一个点，换成三维点，只保留 $0.20$～$3.0\,\mathrm{m}$ 内的点，再按边长 $0.05\,\mathrm{m}$ 的小方块合并相邻的点。第二个节点按 4.2 同样的规则把这些点分成地面和障碍：表面朝上且高度不超过 $0.05\,\mathrm{m}$ 的是地面，其余高度不超过 $1.80\,\mathrm{m}$ 的是障碍，少于 5 个点的零散点团去掉。障碍点发布在 `/vision/obstacles`，每配成一对图像更新一次，局部代价地图把它们标为占用。

下图是全局代价地图。黑色为占用，白色为空闲，灰色为未知。橙色是占用格周围的膨胀带，车身边缘会擦到的一圈。蓝框是足迹，橙箭头是当时车头的朝向。路径必须让蓝框始终留在白色区域里。

![全局代价地图。橙为障碍周围的膨胀带，蓝框为车体足迹](visual-runtime-captures/global_costmap.png)

## 6.2 计算路径

目标点在 RViz 上用 2D Goal Pose 指定，发布到 `/goal_pose`：

```yaml
# /goal_pose  类型 geometry_msgs/msg/PoseStamped，由 RViz 的 2D Goal Pose 发布
header:
  frame_id: map
pose:
  position: { x: ..., y: ..., z: 0.0 }              # 目标位置
  orientation: { x: 0.0, y: 0.0, z: ..., w: ... }   # 到达时车头的朝向
```

收到目标点后，Nav2 开始一次前往该目标的任务。任务以[动作](../01-foundations/05-ros2-communication.md#action)的形式运行，可以反馈进度，也可以中途取消，动作名为 `NavigateToPose`。

任务里的规划步骤由 TF 查出 `base_footprint` 在 `map` 中的位姿作为起点，在全局代价地图上搜索到目标的路径。规划器称为混合 A\*（Hybrid-A\*），它搜索的不只是格子，还包括车头朝向，每一步只沿车真正能开出的圆弧前进或倒退，圆弧的半径不小于这台车的最小转弯半径 $0.80\,\mathrm{m}$。倒车的路段代价乘以 3，路径尽量向前开。得到的路径发布在 `/plan`，是 `map` 坐标系里的一串位姿。任务进行中每秒重新规划一次，使路径跟随车的实际位置和地图的变化。起点或目标落在占用格上时找不到路径，这一次规划失败。

下图绿线是规划出的路径，红圈是目标点，蓝框是车身足迹。路径沿白色区域前进，与两侧的膨胀带保持距离。

![规划出的路径。绿线为路径，红圈为目标点，蓝框为车体足迹](visual-runtime-captures/plan.png)

# 7. 按路径控制速度

到目标的路径已经算出。这一节由 Nav2 的控制器根据路径计算发给底盘的速度，跟踪失败时按顺序恢复，最后由本项目的看门狗在定位不可靠时让车停下。

## 7.1 控制器

路径只是 `map` 里的一串位姿，车要按它行驶，还需要每一时刻的速度。Nav2 的跟踪步骤由控制器完成，本车的控制器称为**模型预测路径积分**（Model Predictive Path Integral, MPPI）控制器。

控制器每秒计算 10 次。每一次，它从当前速度出发，随机生成 1000 组未来 $2.8\,\mathrm{s}$ 的速度序列，每组 28 步、每步 $0.1\,\mathrm{s}$。每组速度按前轮转向车的运动方式推算出一条轨迹，再按几项代价打分：车身足迹碰到局部代价地图里高代价格子的程度、离路径多远、车头与路径方向差多少、离目标多远，以及是否在倒车。倒车一项的权重为 5，车只在必要时倒车。代价越低的轨迹权重越大，控制器把 1000 组速度按权重平均，取平均结果的第一步作为这一时刻的速度。

速度的范围限制为前进 $0.30\,\mathrm{m/s}$、倒车 $0.15\,\mathrm{m/s}$，转动快慢不超过 $1.0\,\mathrm{rad/s}$。车为前轮转向，不能原地转向，车头被障碍挡住时，控制器会给出负的前进速度，先倒车再调整方向。

```yaml
# /cmd_vel  类型 geometry_msgs/msg/Twist，控制器每秒发布 10 条
linear:
  x: ...      # 前进速度，单位 m/s，正为前进，负为倒车
angular:
  z: ...      # 绕竖直轴的转动快慢，单位 rad/s，正为向左
```

下图是同一时刻的局部代价地图：白色为空闲，黑色为不可通行，蓝框是足迹，橙箭头是车头朝向。控制器只依据这块随车移动的图和路径决定这一刻的速度。

![局部代价地图。蓝框为车体，橙箭头为车头朝向，范围随车移动](visual-runtime-captures/local_costmap.png)

## 7.2 跟踪失败后的恢复

Nav2 的任务按本项目提供的行为树执行，失败时依次恢复。规划步骤找不到路径时，先清除全局代价地图，再规划 1 次。跟踪步骤跟不上路径时，先清除局部代价地图，再跟踪 1 次。控制器在 $20\,\mathrm{s}$ 内没能让车移动 $0.25\,\mathrm{m}$，也算跟踪失败。清除代价地图是把相机放进来的障碍抹掉，因为刚看到的障碍可能是噪声，也可能已经离开。

整次任务仍失败时，最多再做 6 轮恢复，每轮轮流执行一项：清除两张代价地图，以 $0.08\,\mathrm{m/s}$ 倒退 $0.25\,\mathrm{m}$，或原地等待 $5\,\mathrm{s}$，然后重新规划。恢复期间收到新的目标点时，直接转向新目标。车不能原地转向，所以恢复动作里没有原地旋转，靠倒退离开被堵住的位置。

## 7.3 看门狗

控制器算出的速度不直接发给底盘。本项目的看门狗节点 [`vo_watchdog`](https://github.com/EnosElinsa/wheeltec-ros-source-reference/blob/62aacaed782091b06060ace276c64e9aaf84ae6b/ros2/navigation/vision-nav/wheeltec_vision_nav/wheeltec_vision_nav/vo_watchdog_logic.py) 接在控制器和底盘之间，订阅 `/cmd_vel`，正常时原样转发到 `/cmd_vel_safe`，底盘订阅的是 `/cmd_vel_safe`。控制器超过 $0.5\,\mathrm{s}$ 没有发来新的速度时，看门狗改发全零速度，不会一直重复旧的速度。

看门狗同时读取视觉里程计的状态。`/odom_info_lite` 标明跟丢、内点数连续 5 帧少于 10，或视觉位姿的四元数无效时，看门狗判为视觉跟丢。

底盘启动时，视觉跟丢本身不会让车停下，因为融合后的运动仍由轮速和陀螺仪维持。视觉跟丢期间，看门狗再检查两件事。第一，轮速超过 $0.3\,\mathrm{s}$ 没有更新，说明底盘数据中断。第二，RTAB-Map 超过 $5\,\mathrm{s}$ 没有定位成功。RTAB-Map 每认出一次地点就在 `/localization_pose` 发布一次车在地图上的位姿，长时间没有这条消息，说明车在地图上的位置已经很久没有修正。两件事有一件成立，看门狗就向 `/cmd_vel_safe` 发全零速度，并取消这次 `NavigateToPose` 任务。`map→odom` 本身不能用来判断，因为 RTAB-Map 即使没有新的修正，也会按固定周期重发上一次的 `map→odom`。底盘不启动时没有轮速可以依靠，视觉一跟丢就停车。

```yaml
# /vision/vo_status  类型 std_msgs/msg/String，看门狗发布的视觉状态
data: "ok"    # ok：正常
              # lost：视觉跟丢，底盘不启动时同时停车
              # lost_wheel_backup：视觉跟丢，但轮速正常，继续转发速度
              # recovering：刚从跟丢中恢复，下一帧正常后回到 ok
```

定位与导航的数据流到此完整。下图把第 5 节到第 7 节排在一起：定位给出 `/map` 和 `map→odom`，占用栅格进入全局代价地图，配对后的深度经障碍点云进入局部代价地图，目标点和全局代价地图进入规划，路径、局部代价地图和 `/odom` 进入控制器，速度经看门狗到底盘。

# 8. 纯视觉方案的问题与改进方向

本章的方案只用一台深度相机感知环境，轮速和陀螺仪只提供车自身的运动。这一节整理这套方案在本车上暴露出的问题，按传感器、运动估计与建图、定位与导航三个层面写出现象和原因，最后针对这些问题列出改进方向，以及每一项的代价。

## 8.1 传感器

### 只有红外可用

这台 D435C 的彩色镜头与深度之间的外参读出来全为零，彩色图像无法与深度图像逐像素对应，本章因此只用左红外。红外图像是灰度的，白墙、浅色地面和窗帘上几乎没有纹理，特征点稀少。

### 投射器交替使可用帧率减半

驱动每秒拍 30 帧，其中只有一半没有散斑，每秒最多配成 15 对。相机元数据里没有投射器状态，只能由图像判断开关。阳光直射时散斑被淹没，两帧的亮点比例相差不到 1.5 倍，这些帧无法判断，只能丢弃。

### 距离误差随距离的平方增长

由 1.1 的公式 $Z = f_x B / d$，视差误差 $\delta d$ 带来的距离误差为

$$
\delta Z \approx \frac{Z^2}{f_x\,B}\,\delta d .
$$

取 $\delta d = 0.1$ 个像素，$Z = 1\,\mathrm{m}$ 时 $\delta Z \approx 5\,\mathrm{mm}$，$Z = 3\,\mathrm{m}$ 时 $\delta Z \approx 4\,\mathrm{cm}$。本章把特征点和栅格的距离上限定在 $3.5\,\mathrm{m}$，就是因为更远的点带来的误差多于约束。

### 视场有限，近处看不到

由内参算出的水平视场角为 $2\arctan\!\big(424 / 421.374\big) \approx 90^\circ$，距离小于 $0.20\,\mathrm{m}$ 时深度图像没有有效距离。车身两侧和车头正下方的矮障碍都在视野之外。前轮转向的车转弯时，车身扫过的区域有一部分从未进入过相机的视野。

### 反光和透明表面

抛光的地砖会在红外里映出倒影，玻璃门几乎不反射红外光。两种情况下深度图像要么没有距离，要么给出倒影的距离，栅格里就会出现不存在的空洞或障碍。

## 8.2 运动估计与建图

### 视觉里程计的计算跟不上输入

在车载的 Jetson Orin NX 上，视觉里程计处理一帧需要 $0.1$～$0.2\,\mathrm{s}$，跟不上每秒 15 对的输入，多出的帧被丢掉。两帧相隔越久，车移动得越多，匹配越难。

### 纹理少的地方视觉跟丢

走廊、白墙前特征点不足 10 个内点时视觉就跟丢，这段时间融合后的运动只靠轮速和陀螺仪。轮子打滑时，这段运动的误差无法由视觉纠正。

### 回环可能认错

办公室里重复的桌椅、相同的柜门会让不同的地方看起来相同。4.1 的固定方差和 4.3 的 3 倍标准差检查能拒绝大部分错误回环，但一条偏差恰好不大的错误回环仍可能被接受，并在局部把地图拉歪。

### 栅格只有一层高度

占用栅格把 $0.10$～$1.80\,\mathrm{m}$ 之间的点压成一层。高于镜头视野的桌面边缘、比 $0.10\,\mathrm{m}$ 还矮的门槛都不会进入地图。建图时经过的行人也会被当成障碍写进地图，行人离开后，这些格子要等车再次看到那里才会被清除。

## 8.3 定位与导航

### 外观变化后认不出地点

定位完全依靠图像是否相同。灯光变化、窗外日照变化、家具换了位置，都会让当前图像与库中记录对不上。识别不出时 `map→odom` 停在旧值，车在地图上的位置随累计误差偏离。视觉同时跟丢并且超过 $5\,\mathrm{s}$ 没有定位成功时，看门狗让车停下。

### 不能原地转向

前轮转向的车无法原地转一圈环顾四周，定位丢失时不能主动换个角度去找熟悉的景物。狭窄处调头要多次前进倒退，每次倒车时相机朝前，看不到车后方。

### 计算资源紧张

相机、配对、视觉里程计、RTAB-Map 和 Nav2 都运行在同一块 Jetson 上。控制器从每秒 20 次降到 10 次，就是为了给其他过程留出计算时间。

## 8.4 改进方向

每一项先写针对的问题，再写改法和代价。

### 恢复彩色与深度的外参

针对只有红外可用和投射器交替。用 Intel 提供的标定工具重新写入彩色镜头的外参后，可以改用彩色图像做特征点。彩色镜头装有红外截止滤光片，看不到散斑，投射器就可以一直开着，深度每帧都可用，也不再需要配对，可用帧率从 15 对提高到 30 帧。代价是需要一次标定，彩色图像在暗处的噪声也比红外大。

### 用左右红外做双目视觉里程计

针对投射器交替和深度误差。投射器关着的那一帧左右红外都没有散斑，可以直接做双目视觉里程计，不依赖深度图像。投射器打开的那一帧仍用来生成栅格。代价是左右匹配在白墙上同样困难，视觉里程计的输入仍是每秒 15 帧。

### 把视觉计算放到 GPU 上

针对视觉里程计跟不上输入。Jetson Orin 带有 GPU，NVIDIA 的 Isaac ROS Visual SLAM 在 GPU 上运行双目视觉里程计和回环，并支持 RealSense 投射器交替的图像。代价是要引入 Isaac ROS 的软件栈，并受 JetPack 版本约束。

### 视觉与惯性紧耦合

针对纹理少时跟丢和快速转弯。把陀螺仪和加速度计的读数直接放进视觉估计，例如换用带 IMU 的 D435i，配合 VINS-Fusion、OpenVINS 或 ORB-SLAM3，视觉短暂失效时由惯性数据维持。代价是要标定相机与 IMU 之间的外参，并让两者的时间戳严格同步。

### 使用学习得到的特征点

针对特征点稀少和外观变化。RTAB-Map 支持用神经网络提取特征点（SuperPoint）并匹配（SuperGlue），在弱纹理和光照变化下比角点更稳。代价是需要 GPU 和模型部署。

### 扩大视野

针对视场有限。在车尾或两侧再装一台相机，或换用视场更宽的相机，倒车和转弯时也能看到障碍。代价是 USB 带宽和计算量随相机数增加。

### 处理行人等动态物体

针对行人被写进地图。在生成栅格之前先检测图像里的人，把对应的深度去掉。代价是多一个检测网络的计算。

### 使用三维栅格

针对栅格只有一层高度。把障碍保存在三维的体素地图里，规划时按车身高度取切片，桌面边缘这类悬空障碍也能被避开。代价是内存和计算量增加。

### 多次建图

针对外观变化后认不出地点。RTAB-Map 支持在同一个数据库里追加多次建图，不同时段、不同光照下的记录都保留下来，定位时任一次记录都可以被认出。代价是数据库变大，识别时要比较的记录更多。

### 加入激光雷达

针对视场有限、距离误差和外观变化。这台车上装有 Livox 激光雷达，用它提供障碍和栅格，相机只负责回环识别，可以同时解决视野和距离精度的问题。代价是方案不再只依靠视觉，还要标定雷达与相机之间的外参。
